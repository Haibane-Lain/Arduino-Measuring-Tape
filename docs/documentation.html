1 · Project overview

The Arduino Measuring Tape is a two-part system: a handheld sensor node that measures distance and a phone application that displays, logs and configures it.

1.1 What it does

  • The UNO node measures distance with an HC-SR04 ultrasonic sensor and streams readings over a Bluetooth SPP link.
  • The phone app shows the live reading on a gauge, keeps a measurement history, and lets the user choose units and alert thresholds.
  • A buzzer on the node provides a local alert when a reading crosses the threshold.

3 · System architecture

3.1 Layering

The mobile app is organised into four layers. Dependencies point strictly downward: screens compose components, components read state, state depends on domain types, and the leaves (theme, utils, config, data) depend on nothing. 

  ┌──────────────────────────────────────────────┐
  │  src/app/**          Routing & screen layout  │   Expo Router
  ├──────────────────────────────────────────────┤
  │  src/components/**   Presentational, reusable │   AppHeader, DistanceGauge, …
  ├──────────────────────────────────────────────┤
  │  src/state/AppState  Single source of truth   │   React context + reducer-ish
  ├──────────────────────────────────────────────┤
  │  src/services/device Domain types + contract  │   Measurement, Settings, DeviceTransport
  ├──────────────────────────────────────────────┤
  │  theme · utils · config · data   (leaves)     │   No knowledge of the app
  └──────────────────────────────────────────────┘

The important property is that no screen imports a hardware API. Screens consume domain types and state; the transport is an implementation detail behind DeviceTransport.

3.2 Data flow

  [ simulated feed / real transport ]
              │  valueCm
              ▼
     AppStateProvider  ── owns: measurements[], settings, connection
              │
              │  useAppState()
              ▼
   ┌──────────┼──────────────┐
   ▼          ▼              ▼
 Distance   History       Settings
 (reads     (reads list   (reads & writes
  current)   + unit)       settings)

There is exactly one list of measurements. The live reading is simply measurements[0], so the hero value and the top history row can never drift apart — there is no second "current value" field to keep in sync.

3.3 Key architectural decisions

DecisionRationale / consequence
Single canonical unit (cm) Every measurement is stored in centimetres; conversion happens only at render time. Changing units never mutates history.
One measurements array Live value = measurements[0]. Removes a whole class of sync bugs.
Screens depend on DeviceTransport types, not BLE Swapping the mock for real Bluetooth is additive; no screen edits required.
Design tokens, not literals All colours, spacing and radii live in one file and can be re-themed globally.
Simulated feed behind a flag The mockup is demonstrable today; the real feed replaces one effect.
Dependency-light interactions Option sheets use the platform Modal instead of a picker library.

4.2 State — AppState

The provider owns three pieces of state and exposes one hook:

useAppState() → {
  connection      : 'disconnected' | 'connecting' | 'connected'
  current         : Measurement | null      // = measurements[0]
  measurements    : Measurement[]           // newest first
  settings        : Settings
  clearHistory()  : void
  updateSettings(patch: Partial<Settings>) : void
}

A useEffect interval drives the simulated feed. Each tick copies the head entry with a jittered value and a fresh timestamp, and leaves the rest of the list untouched: 

const drift = (Math.random() - 0.5) * SENSOR_NOISE_CM * 2;
const nextValue = clamp(round1(head.valueCm + drift), 0, MAX_RANGE_CM);
return [{ ...head, valueCm: nextValue, timestamp: Date.now() }, ...prev.slice(1)];
Seam Replacing the mock means deleting this effect and subscribing to transport.subscribe instead — the rest of the app is unaffected.

DeviceTransport is the single contract the UI is written against. A real implementation wraps react-native-ble-plx (BLE) or a classic SPP bridge and requires no changes to screens.

4.5 Gauge geometry

The dial is a 180° arc drawn with react-native-svg. The arc path runs from the left edge, over the top, to the right edge; the progress arc uses strokeDasharray proportional to the arc length: 

radius   = (size - strokeWidth) / 2
arcLength = π · radius
path     = M (cx − r) cy  A r r 0 0 1 (cx + r) cy
dash     = [ arcLength · (value / max), arcLength ]

7.2 Pin map

SignalUNO pin
HC-SR04 TRIGD9
HC-SR04 ECHOD10
Buzzer +D8 (through 220 Ω)
HC-05 TXDD2 — SoftwareSerial RX
HC-05 RXDD3 — SoftwareSerial TX, via a voltage divider
Hardware caution The HC-05 RXD pin is a 3.3 V input. Feed it through a divider (1 kΩ series + 2 kΩ to GND); driving it directly from a 5 V pin degrades the module over time.

7.3 Sampling algorithm

loop():
  readCommands()                       // parse THRESH: / BEEP: / PING
  if (millis() - lastSampleAt < 200) return     // 5 Hz
  raw = readDistanceCm()               // pulseIn, 30 ms timeout
  if (raw < 0) { emit "DIST:ERR"; return }      // nothing in range
  smoothed += (raw - smoothed) * 0.35  // exponential moving average
  emit "DIST:" + smoothed (1 dp)
  applyAlert(smoothed)                 // buzzer below threshold

readDistanceCm():
  pulse TRIG high for 10 µs
  duration = pulseIn(ECHO, HIGH, 30000 µs)
  return duration · 0.0343 / 2         // cm, speed of sound

Why an EMA? Ultrasonic readings are noisy at the centimetre scale. SMOOTHING = 0.35 weights each new sample at 35 %, damping spikes while staying responsive. It is the first value to tune on real hardware.

7.4 Sketch structure

FunctionResponsibility
setup()Pin modes, Serial + SoftwareSerial at 9600, boot banner

readDistanceCm()Trigger + timed echo; returns −1 on timeout
readCommands()Reads one line from Bluetooth and dispatches
handleCommand()Parses THRESH:, BEEP:, PING

applyAlert()Drives the buzzer when below threshold

8 · Wire protocol

Newline-delimited ASCII, 9600 baud, 8N1. Human-readable so the link can be exercised with any serial monitor.

8.1 Device → phone

FrameMeaning
DIST:<cm>Smoothed distance, e.g. DIST:127.1
DIST:ERREcho timed out — nothing in range
INFO:MEASURING_TAPE_V1Sent once on boot
PONGReply to PING
OK:<key>=<value>Command acknowledged
ERR:<reason>Command rejected

8.2 Phone → device

FrameMeaning
THRESH:<cm>Set the alert threshold, e.g. THRESH:30
BEEP:<0|1>Enable / disable the buzzer
PINGLiveness check

10.3 What works today

  • Navigation — three tabs via Expo Router, themed bar with active-state highlight.
  • Live reading — hero value, gauge sweep, badge and clock all track a simulated feed.
  • Units — switching units immediately re-renders the hero value and every history row.
  • Alert rule — dropping below the threshold flips the badge from green to amber.
  • History — scrollable, newest-first, relative timestamps, clear action.
  • Settings — option sheets, inline numeric threshold, save/clear actions.

10.4 Design decisions

  1. Expo Router + src/app/ — matches Expo guidance and keeps non-route code out of routes.
  2. Single canonical unit (cm) — conversion at render only; history is immutable under unit changes.
  3. Design tokens over literals — one place to adjust the palette.
  4. Dependency-light interactions — platform Modal instead of a picker library.
  5. Transport contract first — screens depend on DeviceTransport types, not BLE.

10.5 Known limitations

  • Sensor feed is simulated; no Bluetooth implemented yet.
  • Firmware is untested on hardware.
  • Alert-based confirmations (Save, Clear) are no-ops on web.
  • No persistence, tests, or reconnect/error states.
  • react-dom pinned to 19.2.3 (see §9.3).

10.6 Next steps

  1. Bluetooth transport — implement DeviceTransport (e.g. react-native-ble-plx) and parse DIST: frames.
  2. Persist history — AsyncStorage or SQLite.
  3. Persist settings — store preferences and push THRESH: on connect.
  4. Bench-test the firmware — flash, verify accuracy, calibrate SMOOTHING.
  5. Device management UX — pairing flow, reconnect handling, "searching" state.
  6. Polish — empty/loading states, alert playback, unit-aware gauge labels, icons/splash.

11.1 Highest-risk items

  • Ultrasonic accuracy — temperature/humidity sensitivity and surface angle; may need calibration or a median filter.
  • Bluetooth module choice — classic SPP (HC-05) vs BLE changes the phone-side library; a decision to lock before Milestone 2.
  • iOS + BLE — classic SPP is not available on iOS; a BLE module may be required for cross-platform support.
